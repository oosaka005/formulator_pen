SUMMARY OF CHANGES
-------------------
Added a per-job "action" option for NORMAL-mode dispense jobs, so a fill and its
corresponding dispense(s) no longer have to happen in the same job:

- enqueue(..., action=...) accepts "FILL", "DISPENSE", or "BOTH" (default "BOTH",
  which is the original always-fill-then-dispense behavior, unchanged).
- action="FILL": draws in the requested volume and seals the valve CLOSED to hold it,
  instead of immediately dispensing.
- action="DISPENSE": opens the valve and dispenses the requested volume from whatever
  is currently held. The amount to move is computed as a %-delta from the actuator's
  *current* live position (read via get_position()) using the same calibrated
  volume<->% line already used for fills, rather than an absolute volume command.
  This lets you queue multiple partial dispenses (e.g. six 0.5 g shots) off of a
  single larger fill (e.g. 5 g).
- If a requested dispense needs more travel than remains above the reference/home
  position (15%, DEFAULT_HOME_POSITION), the move is clamped to that reference
  position instead of overshooting, and the job is flagged instead of silently
  treated as normal.
- Excel output (dispense_results.xlsx) gained two columns: "action" (FILL/DISPENSE/
  BOTH) and "dispense_status" ("OK" or "INSUFFICIENT_VOLUME") so flagged rows can be
  filtered/audited rather than being dropped.
- Refactored the old inline NORMAL-mode fill+dispense steps into two internal helper
  methods (_do_fill / _do_dispense) so FILL/DISPENSE/BOTH can all reuse the same
  valve/pump/logging steps instead of duplicating them. PRIMING mode is untouched.
- main()'s demo job queueing now queues 1x FILL (5 g) + 6x DISPENSE (0.5 g) to
  exercise the new pattern; the old 10x0.15 mL loop is left commented out above it.

FOLLOW-UP CHANGES (after the summary above)
-------------------------------------------
- PRIMING mode's cycle count is now configurable instead of hardcoded. Added
  enqueue(cycles=...) (DispenseJob.cycles, default 1 — matching what the old
  range(1, 2) loop actually ran, despite stale comments claiming "2 cycles"/
  "4 cycles"). The inline PRIMING loop in _execute_dispense was extracted into
  _do_priming(job, profile_token, pwm_in, pwm_out), mirroring the _do_fill/
  _do_dispense split, so its cycle count and print statements reflect job.cycles
  instead of a fixed number.
- Fixed a systematic under-delivery bug in DISPENSE-action %-delta math: it was
  reusing the job's upfront command_volume_ml, which has the fluid profile's
  calibration_offset subtracted (correct for FILL/BOTH, since that offset is a
  bonus that only materializes on a full round trip back to home). A partial
  DISPENSE move never reaches that round-trip event, so the offset was being
  silently lost instead of restored, undershooting by close to that offset's
  magnitude every time. Added _apply_profile_delta_correction(requested_volume_ml,
  profile_slope) — divides by slope only, no offset — and DISPENSE now computes
  its delta volume from job.volume_ml through that instead of through the
  offset-inclusive command_volume_ml.
- Changed INSUFFICIENT_VOLUME handling: previously the move was clamped to
  DEFAULT_HOME_POSITION and executed anyway (dispensing less than requested,
  silently). Now the move is skipped entirely — actuator stays exactly where it
  is — while the job is still flagged INSUFFICIENT_VOLUME and target_percent
  still logs the (unreachable) raw target for diagnostics, instead of dispensing
  an unrequested partial amount.
- Fixed a valve-direction bug in _do_fill: it always moved the valve to UP before
  drawing, assuming a fill always increases the actuator's %. If the actuator is
  already sitting above the new fill's target (leftover position from an earlier
  job/dispense), the "IN" move actually has to travel down to reach it — physically
  a dispense motion, not an intake — so it needs the valve at THRU, not UP. _do_fill
  now compares the live position against job.target_percent before choosing UP vs
  THRU for that first valve move.

WHY move_to_percent_stepped() INSTEAD OF pump_volume() FOR THE DISPENSE ACTION
-------------------------------------------------------------------------------
This isn't a style choice — it's a firmware constraint. On the Pico
(Drivers/pico_api_step.py, Actuator.pump_vol()), the OUT branch of the PUMP command
*always* targets DEFAULT_HOME_POSITION (15%), no matter what volume value is sent —
the volume argument only affects logging/step-size selection for OUT, not the actual
target position. So PUMP:<any volume>,OUT and PUMP:<any other volume>,OUT move the
actuator to the exact same place: fully home. That's correct for a full BOTH-style
dispense (drew X, give back all of X, return home) but it can't do a partial dispense
from mid-stroke — there's no way to tell PUMP "stop after only some of the fluid."
STEP:<target%>,OUT is the only firmware command that accepts an explicit target
percent, so a delta computed from the live position has to go through
move_to_percent_stepped() (which sends STEP), not pump_volume() (which sends PUMP).
Using pump_volume() for a partial dispense would just drive the actuator all the way
to 15% and dispense far more than intended, regardless of any pre-check on the delta.
